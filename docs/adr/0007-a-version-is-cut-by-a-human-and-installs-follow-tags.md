# A Version is cut by a human, and installs follow tags

A Version is a tag on `main` that a Version PR makes: a human raises the number in `package.json`, a check on that pull request refuses a number that is not new and higher or a lock file that disagrees, and a workflow on the push to `main` creates the tag and a GitHub Release whose body is the Version notes, the Version's section of `CHANGELOG.md`, or, when the section is missing, the merged pull request titles since the previous tag. Nothing decides the number but the human, minor when a Spec has closed and patch for what shipped between Specs, because when to cut is a Planning decision (ADR-0001) and the number is the only thing about a Version the pipeline cannot read off the work itself. We tried release-please first and turned it down: it needs a bot to open the pull request, and on this repository that costs a personal access token that expires yearly, a repository setting that lets Actions open pull requests, and a rule that only `feat` and `fix` cut a Version, so a `docs` Ticket that changed the conventions document would reach no Target until something else shipped — all to keep a reminder pull request open that one maintainer does not need. Changesets was turned down earlier for asking every Stage to write a changeset file, a requirement the conventions document would have had to carry into every Target. The Version PR is the one pull request that reaches `main` without a Ticket number, next to the bootstrap exception CONTRIBUTING already names, because a number has nothing for code-review to grade.

Machines install a Version, never `main`: the install command asks npm for the highest tag, so two machines that say `0.2.0` run the same code, which is what lets the number alone stamp a Target's conventions document, a Ticket's State file and a Run's transcripts. A development checkout runs whatever commit it has, so it alone reports the commit beside the number, with a `dirty` mark when the tree has uncommitted changes, because a transcript that names a commit the code did not match is worse than one that names none. The number in a Target's conventions document gives `init` a direction that comparing text never could: an older pipeline leaves a newer document alone and asks to be upgraded, a Run behind the document warns once and names `init`, and neither refuses, since a Target is not worse for last week's copy. A State file a newer pipeline cannot read is named by the sweep, with the Version that wrote it, rather than dropped, because a Stranded Ticket is claimed on the board and nothing but that sweep can find it; new fields are added optional so that case stays rare. The config file gets no version: its schema is strict, so a key an older install does not know is refused by name, and the refusal now says which Version that install is, because on several machines a stale install and a wrong config look the same.

The number says how much Planning has landed, not what changed: minor only when a Spec closes, and everything shipped between two Specs is a patch, a small feature as much as a fix, because the Version notes are where "what changed" is answered. Reading it that way keeps the rule mechanical — did a Spec close, yes or no — and puts the pressure where it belongs: work that deserves a minor deserves a Spec. The first five Versions were cut by hand before the workflow existed, one per Spec closed and one per stretch between them, on the commit that merged the Spec's last Ticket rather than the day its issue was closed; their `package.json` all say `0.1.0`, which only `npm ls` ever shows and the first Version PR corrects.

The Version notes are written by an agent, in the Version PR and never in CI. A generated list of pull request titles was the first answer and was given up because it cannot say the one thing a reader of this tool needs, which is what a Target or its human has to do after upgrading — run `init` again, change the install command, add a config key — since the pipeline rewrites files in every Target it is set up in. The agent runs in the human's own session, from a skill this repository carries, so the notes sit in the pull request and are read before they are published, and the tag workflow stays deterministic with no API key in it. The same skill proposes the number: the rule is mechanical — did a Spec close since the last tag, yes or no — which is what makes it safe to delegate, and the human's review and merge of the pull request is the decision. The five Versions cut before the workflow keep their generated lists.
