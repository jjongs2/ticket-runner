# Landing is a serialized section, not a merge queue

A Run with more than one Lane could let every Ticket rebase, open its pull request, wait for CI and merge independently, and either merge a branch that was green against a Base branch that has since moved, or rebase again just before the merge and pay the Checks and CI a second time. We do neither: the Landing — rebase through the pull of the Base branch after the merge — is a section only one Lane is in at a time, entered in arrival order. The Base branch then cannot move between a Ticket's rebase and its merge, so what CI graded is what lands, and the single-Ticket loop (Checks, Verify, rebase, pull request, CI, merge) is kept as it is. The cost is that a Conflict Stage or a slow CI in one Lane holds every other Lane's Landing, up to about an hour; the time a Ticket spends is in implement and Verify, which stay parallel, so that is the part of the Run we were willing to serialize. We also rejected GitHub's merge queue, which would make a per-repository GitHub setting part of Target readiness and take the order of merges out of the Run's hands.

## Amendment: on a Target that merges by hand, what lands is what CI graded only where GitHub requires it

A Target can leave the merge of a green pull request to a human, setting `merge` to `false` in its config, when its own process has a human review every pull request before it merges. Requiring an approval on GitHub is no way to get that: the pipeline acts as the owner's account, which cannot approve its own pull request, so the owner's merges would be blocked too. Such a Ticket is handed off once its CI is green, and leaves the Landing without the pull after the merge, since nothing was merged.

The Landing could instead be held until the human merged, so that the next Ticket rebased onto a base branch carrying this one. We rejected that: a human merges hours later, and in any order, so holding it would stop every Lane for that long. The later Tickets of the Run rebase onto a base branch without the unmerged ones, and the guarantee this ADR bought no longer holds by itself. On a Target that merges by hand, what lands is what CI graded only when the Target requires a branch to be up to date before merging: GitHub then refuses to merge a pull request whose base branch has moved until it is brought up to date and CI has graded it again. A Target that does not require it may land a squash commit nobody graded against the base branch it lands on, and the configuration page says so beside the setting.

## Amendment: the pipeline runs no Check on a Ticket's branch, and the pull request's CI gates the merge

A Ticket's branch ran its full test suite three times on one tree: in the code Stage, which is told to run the Checks once after its last commit; in the pipeline's Checks right after it; and in the pull request's CI. The transcripts showed the middle run buying nothing. In one Target's 21 Runs (2026-11-21 to 24) the implement and fix Stages ran the full suite after their last change in 46 of 50 Stages, and the tree never changed after that run; the pipeline's Checks then ran that same tree 44 times, 126 minutes in all, every minute of it before verify could start, and none of that Target's 64 Check runs failed. This repository's 17 Runs show the same pattern, and the one fix Stage they sent in for a failing Check was a Host with no installed dependencies, on a docs-only branch the next Run passed unchanged. So the pipeline's Checks caught no defect in a branch in any logged Run, and every Target it has run on lately runs the same commands in CI on its pull requests.

So the pipeline runs no Check on a Ticket's branch: not after an implement or fix Stage, not after a conflict Stage, not when a Run resumes a Ticket. The single-Ticket loop is now (Verify, rebase, pull request, CI, merge): verify starts once the code Stage's work is pushed, and a resolved conflict goes straight on to the pull request. What gates the merge is the pull request's CI, which the Target's owner sets up; the pipeline neither infers nor requires anything about it. A worktree holding changes no commit carries still spends the fix budget before anything grades it. The `checks` setting stays for two jobs: the Stage prompts name the commands, and a red CI is still graded at the branch's merge-base with them, so a base branch that fails them too releases the Ticket with its fix budget as it was. A criterion that asks for nothing but the Checks or CI passing is answered `ci` by verify when a workflow that runs on the pull request runs every command it names, and is ticked once CI passes.

The cost is that a Target without CI now merges code nothing ran: its `ci` row reads `⚠️ no checks` or `⚠️ no workflow runs`, as before, so the table shows nothing graded it. Running the pipeline's Checks beside verify instead, which would have removed the wait and kept a gate for such a Target, was turned down: what gates a Target's merge is its owner's to set up. Opening the pull request before verify, so CI would run beside it, was turned down too: the rebase changes the tree whenever the base branch has moved, which with more than one Lane is often, so CI would run twice. The code Stage keeps running the Checks because it is told to, and nothing forces it; a hook that ran them when a Stage handed in its answer worked, but rested on the CLI's internal tool name and was turned down.
