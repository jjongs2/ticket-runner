# Landing is a serialized section, not a merge queue

A Run with more than one Lane could let every Ticket rebase, open its pull request, wait for CI and merge independently, and either merge a branch that was green against a Base branch that has since moved, or rebase again just before the merge and pay the Checks and CI a second time. We do neither: the Landing — rebase through the pull of the Base branch after the merge — is a section only one Lane is in at a time, entered in arrival order. The Base branch then cannot move between a Ticket's rebase and its merge, so what CI graded is what lands, and the single-Ticket loop (Checks, Verify, rebase, pull request, CI, merge) is kept as it is. The cost is that a Conflict Stage or a slow CI in one Lane holds every other Lane's Landing, up to about an hour; the time a Ticket spends is in implement and Verify, which stay parallel, so that is the part of the Run we were willing to serialize. We also rejected GitHub's merge queue, which would make a per-repository GitHub setting part of Target readiness and take the order of merges out of the Run's hands.
