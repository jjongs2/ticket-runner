# Resume state is a local file, not a tracker comment

Where a Ticket resumes from is written to a gitignored file under `.agent-pipeline/state/`, not to a comment or a label on the issue. The issue is the shared board and everything written there is addressed to a human; a machine-readable resume record posted as a comment would be noise a human has to scroll past and, worse, a second source of truth beside the labels the triage state machine already owns. The State file sits beside the branch and worktree it is about, all three are local, and all three are only meaningful on the machine that has them — a Ticket released on one checkout cannot be resumed from another, which is the cost we accept. It also means `.agent-pipeline/` is only safe to delete when nothing is resumable (CONTRIBUTING.md says so), and that a State file whose worktree has been deleted is ignored rather than trusted: the Ticket is taken from the top instead. That can itself fail at setup, because the branch may still be there, and the Ticket is then handed over with the failure naming it — which is the right outcome, since silently reusing a branch nobody can account for is worse than asking.

We also rejected making this a fourth port beside `Tracker`, `AgentRunner` and `Workspace`. The three ports exist to isolate the effects the pipeline has on the world outside it — GitHub, Claude, git — and a JSON file in the pipeline's own gitignored run directory is not one of those; it is the same kind of local bookkeeping as the Run lock and the Stage transcripts, neither of which is a port either. Whether the branch and worktree the file names are still there *is* the world's business, so that question goes through `Workspace.hasWorktree`. The cost is that the orchestrator tests which reach the release and resume paths run against a temporary repo root rather than purely in memory, which also means those tests assert the file a later Run would actually read.

## Amendment: the file follows the Claim, and the lock says whose it is

The State file is no longer what a released Ticket leaves; it is what a claimed Ticket keeps. It is written as part of the Claim and updated as the Ticket advances, because the Run that leaves nothing behind is the one that was killed rather than the one the rate limit stopped, and a Claim on the board with no resume record beside it is a Ticket a human has to unpick by hand before anything can touch it again.

So the file's presence no longer means "released". Whether a resumable Ticket was released or **stranded** is read from the Claim on GitHub — released if the Claim has come off, stranded if the Ticket still carries this user's assignee and `in-progress` — and the two are resumed by different roads: a released Ticket comes back through the Frontier, a stranded one through the sweep a Run does before the Frontier.

That the sweep may resume a stranded Ticket at all rests on the Run lock, not on a process id. The lock allows one Run per checkout and the State file is local to that checkout, so a Run holding the lock that finds a Ticket still wearing this checkout's Claim knows the Run that wrote the file is not running. We deliberately record no PID and no heartbeat in the State file: a PID on a machine that has since restarted can be another program's, and a heartbeat would make a resumable Ticket depend on how recently a dead Run last wrote to disk. The lock already answers the question the PID would have been asked.

## Amendment: a Hand-off keeps the file too, so a relabel is what resumes a Ticket

The file no longer means "a claimed Ticket". It means work on a branch worth resuming, and a Hand-off leaves as much of that behind as a Release does — it kept the branch and the worktree already, and clearing the file was the one thing that made them unusable. So a Hand-off keeps it, and records the Fix budget as unspent while it is there: the Ticket only comes back through a human's hands, and whatever they did to it is what the fresh budget is for.

There are now three roads back, and the board says which. A Ticket still carrying this Target's Claim is stranded, and the sweep resumes it. One labelled `ready-for-agent` comes back through the Frontier, whether a Release put the label there or a human did. One labelled `ready-for-human` waits: no Frontier can offer it, the sweep passes over it in silence because the Claim has come off, and naming it by hand is refused as not ready. Its file sits inert until a human relabels the Ticket or the issue closes, at which point the sweep forgets it. None of that needed a change to the sweep, and none was made.

One Hand-off is the exception and still clears the file: the Ticket refused at setup over a branch the Run would not branch over. The file exists by then, written as part of the Claim, but no Stage of that Run ever worked in the worktree holding the branch. Keeping it would let a later Run resume into a human's work and run an implement Stage over it, which is what refusing at setup exists to prevent. The distinction is one the code already drew for the draft pull request — whether the hand-off's worktree is one this Run may push out of — and the same answer decides the file.

What carried the decision is the price of misreading a rate limit as an ordinary failure. The runner's rate-limit detection records an occasion when the CLI's wording moved and a Run handed off every Ticket it reached instead of releasing them. The same mistake used to cost a human one deleted branch per Ticket; after this it costs them one relabel. Two things follow from it that are not free. A human may have worked on the branch, so the recorded pull request and Fix budget can be stale by the time a Run resumes — the pull request is taken back out of draft before CI is awaited, and a failure there is a Hand-off, because closing it said the work was not to be continued. And a Ticket taken back from a human keeps the progress table that human read: the Run starts a comment of its own rather than rewriting it, which every other resume still does.
