# A cloud Host is a Claude Code cloud session, and the Run lock lives on GitHub

A Run can execute on a Host that does not need the human's machine switched on: a Claude Code cloud session, which a human opens from the Claude app on the Target and in which an Operator — the session's own Claude — readies the Host, starts the Run in the background, narrowed to the Tickets the human names when they name any, reports what it prints and passes on a Stop. The whole Run moves, not the Stages alone: inside the cloud VM each Stage is still one `claude -p` child process (ADR-0002), which a probe showed is installed there, authenticates through the session's own proxy with no token of ours, and honours `--json-schema`. Local Runs stay first-class, and the two Hosts share a Target by taking turns: one Run per Target at a time, whichever Host it is on.

## Considered options

**GitHub Actions as the cloud Host** was researched side by side and is the better fit on paper: `issues` events start a job natively, the runner has no GraphQL proxy and no push restrictions, `claude setup-token` is documented for CI, and plugins install non-interactively. It lost on two things the human weighs above those: every Run bills Actions minutes against a private Target (a Ticket's Stages take a median 15 minutes, about 2,800 runner minutes a month at the pace this repository ran), and a job is watched in a log page, not steered from the app a human already has in their pocket. It also needs a classic PAT, because a pull request `GITHUB_TOKEN` opens starts the Target's CI only after someone approves it.

**Running only the Stages in the cloud**, with the Run staying local, was dropped first: a cloud session returns no structured result to the process that started it and takes no per-session model, turn limit or schema, which are what ADR-0002 exists to have — and the local machine would still have to stay on.

**An Operator allowed to do more than start, report and stop** — relabel Tickets, or fix code in the checkout — was turned down. The Operator sits in the very checkout whose uncommitted edits break the pull after a merge, and ADR-0001 leaves a human one way into a running Run, the Stop. Everything else still goes through the board. The one addition is releasing a Run lock a vanished Host left behind, which is only ever done when no Run is running.

## What the cloud forced

Five probes against a throwaway repository settled what the documentation does not say:

- **GraphQL is refused outright**, not limited to a pinned set, whatever credentials are supplied. `gh issue create/edit/comment` and `gh pr create/ready/merge` all go through it, so the Tracker adapter talks REST (`gh api`) on every Host, one code path. Turning a pull request back into a draft has no REST form on GitHub; locally it stays GraphQL, and in the cloud it takes the proxy's own `/pulls/{n}/ccr/convert_to_draft` and `/ready_for_review` routes — the only call that differs by Host.
- **Branches push freely** — any name, from worktrees, with `--force-with-lease` after a rebase — but **nothing can be deleted**, neither a branch by `git push --delete` nor any ref through REST, and refs outside `refs/heads/` cannot be pushed at all. A Target must therefore delete a pull request's branch on merge itself, which `init` switches on and Target readiness asks for, and nothing the pipeline keeps on the remote may depend on removing a ref.
- **The proxy appends a "Generated by Claude Code" line** to every issue body, comment and pull request body a cloud Run writes. It cannot be turned off; markers still find the pipeline's own comments, and the squash commit is composed explicitly, so nothing of it reaches `main`.
- **A session waiting on a background process for 25 minutes was not reclaimed.** How long one can run in all is undocumented.
- **A cloud session cannot message a local one back**, so what happens in the cloud reaches a local Host only through the board, the remote, or the human.

`gh` itself is not installed in the VM, and the one `apt` offers is old; with the Tracker on REST its version no longer matters. `gh auth status` calls the proxy's placeholder token invalid while `gh api` works, so readiness asks the latter.

## The Run lock

The lock that keeps one Run per Target has to be visible to every Host, so it moves from a PID file in the checkout to the Target's GitHub repository: a branch that always exists, whose tip commit says who holds it — Host, Run, start — or that nobody does. A Run takes it by pushing a "held" commit on the tip it just read with `--force-with-lease=<ref>:<tip>`, so two Runs that saw the same free tip cannot both succeed (a probe had the second push refused as stale); it releases it by pushing a "free" commit. Nothing is ever deleted, which the cloud would refuse, and a human can see who holds the Target on GitHub.

Who decides that a holder is dead is the part that is surprising. On the Host the holder ran on, the lock's Host and process start time answer it exactly as the PID file always did, and a Run there takes a dead holder's lock over — so a local Run ended by Ctrl+C costs nothing, as before. Across Hosts nothing can answer it, and **a lease that expires unless the holder keeps renewing it was rejected**: it would make a live Run lose its Target to a missed heartbeat, and it reintroduces for the lock the dependence on how recently a process last wrote that ADR-0004 refused for the State file. A lock a Run on another Host left behind therefore stays until a human releases it — through an Operator, or by committing to the lock branch on GitHub. A cloud VM reclaimed mid-Run costs one such release, and the Stranded Tickets it left are swept by the next Run as usual.

## Getting the pipeline and its plugin onto a cloud Host

A cloud VM starts empty. Neither user-level plugins nor `enabledPlugins` load in a cloud session, but `claude plugin marketplace add` and `claude plugin install` work inside the VM, and the plugin's skills then resolve in a nested `claude -p`. Whatever the cloud environment's own setup script already installed — the pipeline, the plugin — is used as it is; the Operator installs only what is missing, the pipeline at the Version the Target's conventions document is stamped with. A setup script's copy therefore wins over the stamp: which Version runs is recorded on the State file and transcripts either way, and the stamp decides only where nothing was installed. That is why Target readiness asks for the stamp on every Host, where ADR-0007 only warns about which Version it names.

The Operator's instructions have to come from the repository, the only thing a cloud session carries over, so `init` puts them in the Target as a project skill, and Target readiness asks for it on every Host — a Target a local Run accepts is one an Operator can run from the app, rather than one that says "run `init` first" at the moment the human has only their phone.

The Lane count stays in the Target's config, but a Run can be told otherwise where it starts, because how many Lanes a Host can carry is the Host's business.
