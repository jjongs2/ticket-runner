# Stop is a signal, and Ctrl+C stays a kill

A Stop — finish the Tickets the Lanes hold and take no more — reaches a Run as SIGTERM, which `agent-pipeline stop` sends to the process the Run lock names, and nothing else: no stop file beside the lock and no meaning for Ctrl+C. A file would need an owner for its lifetime (who removes it, and whether one left by a killed Run stops the next one before it starts) and a moment the Run reads it, which is only when a Lane comes free, so the request would be acknowledged late; a signal arrives at once, leaves nothing behind, and the lock already holds the process id and the liveness check the `stop` command needs. Ctrl+C could have meant Stop too, but the Stages are spawned in the Run's own process group, so the terminal delivers SIGINT to every `claude` session as well as to the Run; making it graceful means detaching the Stages into their own group, which reopens the kill path that took two bugs (#11, #40) to get right. Instead Ctrl+C and SIGKILL stay what they are, a kill that leaves Stranded Tickets for the next Run's sweep (ADR-0004), and the two ways to end a Run early are told apart by what they leave: a stopped Run leaves nothing stranded, a killed one does. That kill is Ctrl+C in the Run's own terminal, and `stop` says so when it is asked: SIGINT sent to the Run's process id alone, from another terminal, ends the Run and leaves the Stages running with nobody to read them. A second SIGTERM is ignored rather than escalated to a kill, and there is no way to take a Stop back, because the lock is held until the Lanes are back and a new Run is the way to carry on.
